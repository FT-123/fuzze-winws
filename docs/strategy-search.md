# Как подбирать стратегии обхода DPI: проект нового поиска

> **Статус:** базовая версия реализована в `diagnostics.py`, `strategy_model.py`,
> `search_planner.py` и `fuzzer_engine.py`: диагностика, canary-поиск,
> подтверждение, минимизация и запись `auto-config.bat`. Портфель профилей
> и runtime-`circular` остаются следующими шагами.

Документ описывает, что меняет zapret2 и `blockcheck2`, почему старый «фаззер»
плохо подходил для реального подбора и как устроен поиск в этом приложении.

Источники: `zapret2/docs/readme.md`, `zapret2/docs/manual.md` (разделы `blockcheck2`,
`circular`, `wssize`), `blockcheck2.sh`, `blockcheck2.d/standard/*`, `lua/zapret-auto.lua`.

---

## 1. Что важно из README zapret2

1. **Стратегия — это программа, а не набор флагов.**
   `--lua-desync` задаёт последовательность инстансов `функция:параметр=значение:...`.
   Порядок вызовов — часть стратегии (`wssize` обязан идти до `syndata`, иначе окно
   модифицируется после отправки). Плоский перебор `--dpi-desync-*` из zapret1
   описывает лишь малую часть пространства.

2. **Пейлоад и диапазоны — это не «оптимизация», а часть стратегии.**
   `--payload=tls_client_hello`, `--out-range=-d10` отсекают пакеты на уровне C
   до вызова Lua. Правильный фильтр одновременно:
   * снижает нагрузку в десятки раз;
   * не даёт стратегии срабатывать на чужих пейлоадах;
   * ограничивает число пакетов, к которым применяется десинк.

3. **Функции можно комбинировать и повторять.**
   Нет фиксированных фаз `fake,split`; можно послать несколько фейков с разными
   фулингами, вставить `pktmod`, `tls_mod`, `repeats`, `tcpseg`, `drop`.
   Значит, поиск должен уметь добавлять/удалять/переставлять инстансы, а не только
   менять числовые параметры.

4. **Блобы вместо жёстких fake-файлов.**
   `--blob=name:0xHEX|[+ofs]@file`. Автоматическая TCP-сегментация снимает ограничения
   на размер фейка/`seqovl`, но добавляет параметры, которые надо проверять.

5. **`circular` и `zapret-auto` — это готовый runtime-механизм адаптации.**
   `zapret-auto.lua` умеет считать неудачи по хосту (RST, ретрансмиссии, DPI-редиректы),
   а `circular` — переключать стратегии по кругу при превышении порога. Это лучше,
   чем один «магический» конфиг, который ломается при смене DPI.

6. **`--debug` — главный инструмент диагностики.**
   По логу видно, какой payload распознан, какой инстанс сработал, был ли cutoff,
   не улетел ли фейк на сервер. Без анализа лога поиск вслепую.

7. **Ограничения, которые нельзя обойти стратегией:**
   * подмена DNS — лечится DoH/своим DNS, а не winws;
   * полный блок IP/порта — zapret не поможет;
   * TLS 1.2 сложнее TLS 1.3: в `ServerHello` сертификат виден DPI;
     `wssize` — крайняя мера, снижает скорость и не дружит с хостлистами.

## 2. Что не так с текущим фаззером

Сейчас `FuzzerEngine.generate_mutations()` выдаёт ~50 плоских комбинаций
`tcp_split/seqovl/ttl/desync/fooling/repeats/cutoff/any_protocol` и проверяет каждую
на всех доменах. Это:

* не различает HTTP / TLS 1.2 / TLS 1.3 / QUIC;
* не проверяет DNS и IP-блоки, поэтому часто «ищет» там, где обход невозможен;
* не использует `--payload`/`--out-range` и не понимает Lua-стратегии winws2;
* не делает повторных попыток, поэтому принимает нестабильные стратегии за рабочие;
* не проверяет пересечение по нескольким доменам (стратегия может работать только на одном);
* не минимизирует найденную стратегию (лишние фейки, TTL, повторы);
* не различает «работает без обхода» и «сломалось из-за DPI»;
* не умеет собирать портфель профилей и включать `circular`.

## 3. Предлагаемый метод: 5 шагов

Назовём его **DSMP**:

1. **Diagnose** — определить, что именно блокируется.
2. **Select family** — выбрать класс стратегий под тип блока и протокол.
3. **Search** — искать внутри класса, от простого к сложному, с ранним выходом.
4. **Minimize** — убрать всё лишнее из найденной стратегии.
5. **Portfolio** — собрать несколько профилей и, при желании, `circular`.

### Шаг 1. Диагностика (до любого перебора)

Для каждого домена и семейства адресов:

1. **DNS**
   * системный резолв vs DoH (`cloudflare-dns.com`, `dns.google`);
   * если IP расходятся — фиксируем подмену DNS;
   * для тестов стратегий используем IP из DoH и `curl --resolve`,
     иначе тестируем не DPI, а сломанный DNS;
   * в отчёте: «DNS подменён — winws не поможет, включите DoH/DoT или hosts».

2. **Доступность без обхода**
   * HTTP (80), TLS 1.2 (443), TLS 1.3 (443), QUIC/HTTP3 (443) — с коротким таймаутом;
   * если всё работает — обход не нужен, не тратим время.

3. **IP-блок**
   * `iana.org` на IP заблокированного домена и заблокированный домен на IP `iana.org`
     (через `--resolve`, без проверки сертификата — это диагностика, а не успех);
   * полный блок IP/порта → прекращаем поиск и объясняем причину;
   * частичный блок (TCP проходит, дальше RST/тишина) → пробуем стратегии.

4. **Классификация блока**
   * `dns`, `ip`, `tcp_handshake`, `sni`, `tls12_server_hello`, `tls13`, `http`, `quic`;
   * тип блока определяет порядок семейств и делает поиск в разы короче.

5. **Отпечаток сети**
   * публичный IP/ASN, шлюз, DNS, версия winws/winws2;
   * результаты кэшируются по этому отпечатку.

### Шаг 2. Семейства стратегий

Не перебираем всё подряд. Для каждого payload-типа используем каталог семейств,
упорядоченный по стоимости и вероятности:

| # | Семейство | Когда пробовать | Пример |
|---|-----------|-----------------|--------|
| 1 | Split / disorder | SNI-блок, простой DPI | `multisplit:pos=1,midsld` |
| 2 | Fake + TTL | DPI режет по SNI/протоколу | `fake:blob=fake_default_tls:ip_ttl=4` |
| 3 | Fake + fooling | DPI проверяет TCP-опции/seq | `fake:...:tcp_md5`, `badsum`, `tcp_seq=-3000` |
| 4 | Faked split/disorder | DPI собирает поток, split не проходит | `fakeddisorder:pos=midsld:ip_ttl=4` |
| 5 | Hostfake | Нужно подменить SNI/Host | `hostfakesplit:host=www.google.com` |
| 6 | Fake + split | Комбинированный блок | `fake` + `multidisorder` |
| 7 | wssize / syndata | Блок по окну/рукопожатию; TLS 1.2 | `wssize` → `syndata` → split |
| 8 | QUIC fake | Блок QUIC/HTTP3 | `fake:blob=fake_default_quic:repeats=11` |

Правила порядка:

* TLS 1.2: сначала fake/faked с TTL — заставить DPI принять ClientHello и не смотреть
  на сертификат в ServerHello; `wssize` — последним.
* TLS 1.3: достаточно клиентской части, семейства 1–6.
* HTTP: `method+2`, `midsld`, fake HTTP.
* QUIC: только `quic_initial`, fake QUIC.
* `wssize` не применять к профилям с hostlist (ограничение движка).

### Шаг 3. Поиск

**3.1. Ленивая генерация.**
Кандидаты не строятся списком целиком — генератор отдаёт их по одному, движок
останавливается на первом успехе. Внутри семейства параметры идут от дешёвых к дорогим.

**3.2. Canary-домен.**
Сначала кандидат проверяется на одном «канареечном» домене (1 попытка). Только если
он прошёл — на всех целевых доменах, с повторами. Это убирает 80–90% проверок.

**3.3. Пересечение.**
Стратегия считается найденной, только если проходит все выбранные домены
(или заданный порог). Иначе — это стратегия для одного домена, её место в портфеле.

**3.4. Повторы.**
2–3 попытки на домен, каждая — новое соединение. Требование: все попытки успешны
(standard/deep) или большинство (quick). Это отсекает «повезло один раз».

**3.5. TLS 1.2 / 1.3 раздельно.**
Для TLS 1.2 проверяем сертификат (без `-k`). Для TLS 1.3 — handshake. HTTP — код
ответа и отсутствие редиректа на другой SLD. HTTP 400 после fake — признак утечки
фейка на сервер, кандидат отбрасывается.

**3.6. Уровни.**
* **quick** — 1 попытка, только семейства 1–2, ранний выход;
* **standard** — 2 попытки, семейства 1–6, TTL 1–12, autottl 1–3;
* **deep/force** — 3 попытки, все семейства, повторы, `wssize/syndata`, QUIC,
  без пропуска семейств после успеха.

**3.7. Обратная связь из `--debug`.**
Запускать winws2 с `--debug`, читать лог:
* payload не распознан → не тот `--payload`;
* `instance cutoff`/range → слишком узкий диапазон;
* `error`/`unknown blob` → кандидат невалиден;
* fake дошёл до сервера (400) → убрать/заменить fake.

Это позволяет отбрасывать кандидатов **до** сетевой проверки.

### Шаг 4. Минимизация (delta debugging)

После успеха не оставляем «всё, что сработало». Убираем по одному:

1. лишние инстансы (если их больше одного);
2. `ip_ttl`/`ip6_ttl`/`autottl`;
3. фулинги (`tcp_md5`, `badsum`, `tcp_seq`, ...);
4. `repeats` (уменьшаем до 1);
5. `tls_mod`/`seqovl_pattern`;
6. лишние профили.

После каждого удаления — полная проверка на всех доменах. Если стало хуже — возвращаем.
Результат: минимальная стратегия, меньше нагрузки, меньше ложных срабатываний и
меньше шансов, что DPI зацепится за лишний признак.

### Шаг 5. Портфель и runtime-адаптация

Один конфиг — плохая цель. Итог поиска:

* профиль на каждый сервис/группу доменов (YouTube, Discord, Telegram, общий);
* минимальные стратегии для каждого;
* общий fallback;
* опционально `circular` в winws2: 2–3 стратегии на хост, переключение по
  `fails/time` и детекторам неудач (`RST`, ретрансмиссии, DPI-редирект).

`circular` требует входящих пакетов (`--in-range`), поэтому включается осознанно:
он дороже по CPU, но переживает смену DPI и балансировку провайдера.

## 4. Модель стратегии в коде

Нужен не `WinwsParams`, а дерево:

```text
Strategy
├── Profile (фильтры: tcp/udp, порты, l7, hostlist, ipset)
│   ├── Group (scope: payload, in-range, out-range)
│   │   ├── Instance(function, ordered params)
│   │   └── Instance(...)
│   └── Group(...)
└── Profile(...)
```

### Парсер winws2

* Делим батник по `--new` (уже есть).
* Внутри секции идём токенами; `--payload`, `--in-range`, `--out-range` меняют группу.
* `--lua-desync=func:p=v:p2` → `LuaInstance`.
* Храним **порядок** параметров и неизвестные параметры без изменений.
* Правим только span инстансов, остальные флаги, `--lua-init`, блобы не трогаем.
* Применяем изменения от конца файла к началу, чтобы не сбить смещения.

Ограничения (грамматика):

* `fake`/`send` требуют `blob`;
* `seqovl`/`seqovl_pattern` — только к split-функциям;
* `tls_mod` — только к TLS fake;
* `wssize` — до `syndata`/split, не с hostlist;
* `drop`/`send`/`pktmod` — отдельные вердикты, порядок важен.

### Генератор winws2

Для каждой группы (по payload) отдаёт последовательности инстансов:

```text
[ split(pos) ]
[ fake(blob, ttl, fooling, repeats) ]
[ fake(...) ] + [ split/disorder(pos) ]
[ fakeddisorder(pos, ttl, fooling) ]
[ hostfakesplit(host, pos) ]
[ wssize ] + [ syndata ] + [ split ]
[ fake(blob=fake_default_quic, repeats) ]
```

Для сервисных групп сохраняем их `tls_mod`, `sni`, кастомные `blob`
(например, YouTube `sni=www.google.com`), подставляя их в шаблон.

### Совместимость с winws1

`WinwsParams` остаётся для старых `.bat`, но поиск идёт тем же каскадом:
split → fake+TTL → fooling → faked → hostfake → combos.
Патчер уже умеет не ломать `--new`-секции и `any-protocol`.

## 5. Оценка кандидата

Функция полезности:

```text
score = success_rate
      * stability_factor      # все попытки / большинство
      * protocol_coverage     # http/tls12/tls13/quic
      - cost_penalty          # число инстансов, repeats, ширина диапазона
      - risk_penalty          # fake-утечки, редиректы, TTL-аномалии
```

Порядок выбора:

1. все домены прошли, все попытки, TLS 1.2 и 1.3;
2. все домены, но не все попытки;
3. большинство доменов (кандидат в портфель, не глобальный);
4. один домен (только специализированный профиль).

---

## 6. Что это даёт

* Вместо ~50 случайных конфигов — **10–30 осмысленных** проверок в типичном случае
  SNI-блока, и ранний выход.
* Отсекаются DNS/IP-блоки, где обход невозможен, — не тратим минуты впустую.
* TLS 1.2 и 1.3 проверяются раздельно — не «лечим» не тот слой.
* Повторы и пересечение доменов убирают ложные успехи.
* Минимизация даёт более быстрый и менее заметный конфиг.
* Появляется поддержка winws2/Lua и портфель профилей вместо одного `.bat`.

## 7. План внедрения в этот репозиторий

### Этап 1. Фундамент

* `strategy_model.py` — AST winws2, парсинг/эмиссия, определение движка.
* `diagnostics.py` — DNS/DoH, «работает без обхода», матрица HTTP/TLS1.2/TLS1.3/QUIC,
  классификация блока.
* `probe.py` — TLS1.2/1.3, `--resolve` по DoH-IP, повторы, проверка редиректов/400.
* UI: режим `Quick / Standard / Deep`, отчёт диагностики в журнале.

### Этап 2. Поиск

* `search_planner.py` — ленивые генераторы семейств для winws1 и winws2.
* `FuzzerEngine.run_fuzzing` — canary → подтверждение → пересечение → запись.
* Минимизация winws2 по инстансам и параметрам; winws1 — по полям.
* Тесты: парсер round-trip, порядок кандидатов, грамматика, классификация.

### Этап 3. Портфель

* Генерация multi-profile `.bat` с лучшими стратегиями по группам.
* Опциональный `circular` с 2–3 стратегиями.
* Кэш результатов по отпечатку сети.
* Экспорт отчёта: что проверено, что прошло, почему остальное отброшено.

## 8. Псевдокод основного цикла

```python
report = diagnostics.run(targets)
log(report)

if report.dns_poisoned:
    warn("DNS подменён: включите DoH/DoT, winws не поможет")

if report.ip_blocked:
    warn("Полный блок IP/порта: обход стратегией невозможен")
    return

canary = report.choose_canary(targets)

for family in families_for(report, mode):
    for candidate in family.generate(baseline, mode):
        if not probe(candidate, canary, attempts=1):
            continue
        if not probe(candidate, targets, attempts=attempts, require_all=True):
            continue
        if mode != "quick":
            candidate = minimize(candidate, targets)
        if confirm(candidate, targets, attempts=3):
            apply(candidate)
            save_session(candidate, report)
            return candidate

build_portfolio(best_per_family)
```

## 9. Итог

«Лучший способ» — не увеличивать число комбинаций, а **сузить пространство**:

1. сначала понять, что и где блокируется (DNS/IP/SNI/TLS/QUIC);
2. идти по проверенным семействам от простого к сложному;
3. проверять на одном домене, подтверждать на всех и с повторами;
4. минимизировать найденное;
5. оставлять портфель и, где возможно, `circular`, а не один хрупкий конфиг.

Именно так устроен `blockcheck2` + `zapret-auto`, и это на порядок эффективнее
плоского перебора флагов.
